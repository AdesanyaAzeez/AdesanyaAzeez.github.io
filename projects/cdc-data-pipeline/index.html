CASE STUDY · DATA REPLICATION

CDC Data
Pipeline

Incremental, low-impact replication pipelines from operational databases into ClickHouse — designed for schema drift safety, correct cursor state, deduplication, and provable consistency across high-volume datasets.

Airbyte MySQL ClickHouse CDC Python SQL
Role Replication & pipeline engineering owner
Area CDC · ingestion · consistency engineering

Context

The warehouse was powered by a growing number of upstream operational databases. As table sizes and write volumes grew, the previous batch-driven nightly strategy became unsustainable — reads against source databases were heavy, freshness was measured in hours, and failures required re-running full loads that could take an entire night.

The organisation needed a replication strategy that was incremental by default, low-impact on sources, able to survive mid-stream failures without correctness loss, and honest about when a stream was or was not consistent with source.

Problem

The previous strategy combined correctness and performance problems:

  • Source-impactful batches. Full nightly table scans on operational OLTP databases during the busy window.
  • Poor freshness. Intra-day changes were invisible in the warehouse until the next batch completed.
  • Unrecoverable state. No persisted cursor contract — retries or partial runs silently duplicated rows or skipped them.
  • Untrusted outputs. No consistency checks between source and target, so silent integrity issues could persist for weeks.

Approach

CDC-first, with an explicit state contract and an equally explicit set of post-sync checks that every stream must satisfy before it is marked green:

  1. Binlog CDC for high-volume sources. Row-level changes streamed with minimal source read footprint, instead of scans.
  2. Unified cursor state. Persisted per-stream watermark with checksums and compare-and-swap semantics so any stream can resume or reset.
  3. Idempotent writes + dedupe keys. Target writes are re-runnable; composite dedupe keys + insert_id ordering guarantee uniqueness on materialization.
  4. Consistency checks. Automated row-count diffs for bounded windows plus row-hash sampling across representative ranges.
  5. Schema drift hold. Column additions / deletions trigger an alert and a configurable stream-hold rather than silently breaking the target mapping.

Architecture & Implementation

Each replication stream passes through five explicit stages:

  • Extract (CDC). Binlog-based CDC connectors for write-heavy sources; batched incremental cursors for low-volume sources where binlog access was not available.
  • State (Cursor). A persistent, per-stream watermark with compare-and-swap semantics — two concurrent syncs cannot both advance the cursor.
  • Write (Idempotent). Target writes use a natural primary key plus an insertion sequence id; a short merge dedup step re-runs post-sync to handle retries cleanly.
  • Materialize. Final target tables are rebuilt from the idempotent landing layer; downstream consumers never query the raw landing layer directly.
  • Validate. Consistency checks for every sync: row-count diff for recent bounded windows; row-hash sampling across a configurable set of key-buckets.

Key Engineering Challenges

  • Schema drift. Column additions, removals, or type changes in a source silently broke mappings. Solved by introducing schema contracts: a stream detects drift, raises an alert, and optionally holds ingestion before downstream marts break.
  • Duplicates on resume. Any pipeline interruption could re-read the same window. The composite dedupe key + ordered insert_id pattern makes re-runs safe and re-playable.
  • Cursor race conditions. Two concurrent sync attempts could both advance the cursor. State store uses a compare-and-swap transaction plus a singleton lock per stream.
  • Out-of-order events. Binlog delivery can occasionally arrive out of order. Introduced a small watermark lag-tolerance window and a periodic merge re-org to finalize rows once their event horizon has closed.

Outcome & Impact

−78%

Read impact on source operational databases switching from batch full-table scans to CDC-based incremental streaming.

24h → 9m

High-value streams freshness: warehouse latency reduced from a full day cycle to single-digit minutes for most tables.

0 silent

No undetected integrity issues across six months of audit logs; every drift or failure was surfaced by sync-time checks.

The state contract and runbook also changed new-stream economics: a new source could be on-boarded with the same schema, state, and checks template inside a single working day — versus a multi-week bespoke design per source on the old approach.
